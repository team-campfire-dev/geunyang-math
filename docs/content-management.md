# DB 콘텐츠 관리

2026-09-17 · 코드 기준: [편집 화면 정리 #52](https://github.com/team-campfire-dev/geunyang-math/pull/52), `a984737`. 릴리스별 검증은 [배포 기록](deployment.md#릴리스별-검증-기록)을 따른다.

기본 콘텐츠와 이후 발행한 콘텐츠의 운영 원본은 MySQL이다. 수업·진단 문항·개념 이름을 TypeScript/JSON 파일에서 불러오는 런타임 경로는 없다.

2026-09-16에 저장 구조가 바뀌었다. **발행된 판본은 JSON 한 덩이가 아니라 행이다.** 무엇이 어느 표에 있는지는 아래에 적고, 어떻게 옮겼는지는 [배포 기록](deployment.md#저장-구조-migration)에 있다.

## 저장 구조

판본이 아닌 **정체**가 먼저 있다. 수업·진단은 반드시 코스 하나에 속하고([용어 사전](glossary.md)), 그 소속은 판본이 아니라 정체의 것이다.

- `Course`: 코스. 키·이름·한 줄 소개. 얼리지 않으므로 고치면 곧 반영된다. 지금은 플랫폼의 `fractions` 하나다.
- `Lesson`: 수업의 정체. 어느 코스에 속하는지와 **코스 안 순서**(`order`)를 든다. 첫 초안을 만들 때 생기므로 판본이 없는 수업은 「아직 발행되지 않은 수업」이고, 카탈로그와 health는 판본이 있는 것만 센다. 초안이 하나뿐인 수업의 초안을 지우면 정체도 함께 사라진다.
- `Diagnostic`: 진단의 정체. 어느 코스에 속하는지.
- `ProblemSet`: **문제집**의 정체. 어느 코스에 속하는지와 이름(`name`). 수업을 쓰다가 단계에 문제를 더하면 그 자리에서 이름 없이 생긴다. 이름을 주는 것이 재사용하겠다는 선언이다(이름을 주는 화면은 아직 없다). **한 문제는 문제집 하나에만 속한다.**

판본을 식별하고 목록에 세우는 것은 판본 표의 칸이고, 판본의 **내용**은 세 표에 나뉘어 있다.

- `LessonVersion`: 수업 판본. `metadata`가 수업 자신에 대한 것(`public`)과 **복습 풀**(`review` — 복습 과제가 문제를 고르는 문제집 참조, 없으면 null)을 담는다. 문제는 여기 없다 — 단계의 `core.problem_set@2` 블록이 `{ problemSetId, problemSetVersionId, problemVersionIds }`로 문제집을 **참조**할 뿐이다. 순서도 여기 없다 — `Lesson.order`가 코스 안 자리다.
- `ProblemSetVersion`: 문제집 판본. 문제는 `PublishedProblem` 행이고 블록은 `ContentBlock` 행이며, 둘 다 이 판본 ID에 매달린다. 판본 ID는 수업·진단과 같은 이름 공간을 쓴다.
- `DiagnosticVersion`: 진단 이름·설명·예상 시간·발행 시각과, 문항을 가져오는 문제집 참조(`problemSetId`·`problemSetVersionId`·`problemVersionIds` — 묻는 순서). 문항은 여기 없다. `diagnosticKey=starting-point`의 최신 발행 판본을 새 진단에 사용한다.
- `Concept`: **개념**. 전역이고 키는 불변이다. 공통 사전의 호칭(`label`)과 **문제가 이것을 평가할 수 있는가**(`assessable`)를 든다. 수업이 가르치고 전제하는 개념과 문제가 평가하는 개념은 `assessable`이어야 한다. 표시 순서는 없다 — 코스의 수업 순서(그 개념을 처음 가르치는 수업)에서 유도한다.
- `ConceptDefinition`: 범위별 **뜻풀이**. `(conceptKey, scopeKind, scopeKey)`마다 한 행이고, 이 범위에서 부르는 이름(`label`, 비어 있으면 개념의 이름)과 선택 요약·설명 맥락(`usageNote`)을 든다. 본문은 `ContentBlock` 행이다. **판본도 초안도 없다** — 어떤 판정에도 쓰이지 않으므로 되찾을 과거가 없고, 저장이 곧 최신이다. 블록이 없는 행은 호칭만 바꾼 것이라 본문에서 걸 수 없다.

내용을 가진 세 표:

- `LessonSection`: 수업의 섹션을 보여 주는 순서대로.
- `PublishedProblem`: 문제집 판본이 가진 문항의 이름·순서와, 블록이 아닌 것(개념 키·응답 형식·채점 규칙·힌트 유무). 발행된 문항은 모두 문제집의 것이라 `ownerKind`는 `problem_set` 하나다. 진단도 문제집을 참조한다.
- `ContentBlock`: **발행된 판본이 가진 모든 블록과 뜻풀이의 본문.** 수업의 섹션 본문, 문항의 지문·힌트·해설, 뜻풀이의 본문이 모두 여기 있고 `ownerKind`(`section`·`problem`·`definition`)와 `slot`으로 갈린다.

문항 하나를 읽는다는 것은 `PublishedProblem` 한 행과 그 문항의 `ContentBlock` 행들을 합치는 일이고, 수업 하나를 읽는다는 것은 `metadata`와 `LessonSection`·섹션 블록을 읽은 뒤 블록이 참조하는 문제집 판본에서 고른 문제를 가져오는 일이다(`lessonRecords`). 진단도 같은 길로 문제집 판본에서 문항을 가져온다(`diagnosticRecords`). 문항의 형은 하나다 — 해설은 없어도 되고, 해설·힌트를 보여 줄지는 문항이 아니라 그것을 내는 쪽(수업·과제 정책·진단)이 정한다. 카탈로그·수업 화면·진단·용어·초안 만들기·번들 내보내기가 모두 이 경로로 읽는다.

두 가지 규칙이 이 구조를 지탱한다.

- **판본 ID는 수업·문제집·진단을 통틀어 겹치지 않아야 한다.** 블록이 자신을 가진 판본의 ID로 매달리므로, 겹치면 한쪽 판본의 블록이 다른 쪽 것으로 읽힌다. 등록할 때 검사한다. 뜻풀이의 블록은 생성된 행 id에 매달리므로 작성자가 지은 이름과 겹칠 수 없다.
- **블록의 `fallback`은 없는 키다.** 비어 있는 것이 아니라 아예 없는 것이고, 행에서는 NULL로 두고 읽을 때 키를 만들지 않는다. null로 되살리면 판본 해시가 달라져 이미 발행한 판본이 불변 위반으로 거부된다.

`content:verify`는 모든 판본을 행에서 도로 맞춰 검증 규칙과 참조를 통과하는지 보고, 어느 판본에도 속하지 않는 행이 없는지 센다. 섹션 행이 빠지면 `sectionCount`가 어긋나고, 문항 행이 빠지면 수업이 문제집 판본에 없는 문항을 가리키므로 둘 다 걸린다. 블록 하나의 내용이 조용히 달라지는 것은 비교할 상대가 없어 걸리지 않는다 — 발행된 판본의 사본을 지운다는 것이 그런 뜻이고, DB의 다른 표들과 같은 처지다.

판본이 아닌 JSON도 남아 있다.

- `ContentDraft.document`: 작업 중인 초안은 지금도 JSON 한 덩이다. 발행된 판본이 아니므로 불변도 아니고 쪼갤 이유도 없다. 초안은 `ownerKind`로 수업(`lesson`, `ownerKey`=수업 키)과 문제집(`problem_set`, `ownerKey`=문제집 ID)으로 갈리고, 수업 초안이 참조하는 문제집 초안은 수업과 **같은 트랜잭션에서 함께 발행**된다.
- `Enrollment.lessonVersionId`, `Assignment.problemSetVersionId`, `DiagnosticRun.document`: 수강·과제는 시작할 때의 판본을 계속 참조하고, 진단은 복사해 보존한다. 과제 항목은 문제 ID와 순서만 들고 내용은 문제집 판본에서 읽는다.

블록은 DB 안의 확장 가능한 형식이다. `kind`, `typeVersion`, `payload`, `required`, `fallback` 계약은 유지한다. 기존 블록으로 만든 콘텐츠는 앱 재배포 없이 등록할 수 있다. 새로운 그래프·도형 블록 종류는 검증 스키마와 웹/모바일 렌더러를 추가한 뒤 배포해야 한다.

rich text는 `$...$`, `$$...$$`, `\(...\)` 안에 LaTeX를 담고, 도형 캡션과 그림 안의 `text` 도형은 한 줄로 표시하므로 인라인 형태만 쓴다. 수식 안에 한글을 넣으면 화면에 오류 표시가 나오므로 단위와 조사는 수식 밖에 둔다. 화면 낭독용 이름에는 수식 표기를 쓰지 않는다. `core.figure@1`은 `alt`가 그림 전체의 이름이고, `math.fraction_strip@1`은 수식 `label`을 쓸 때 평문 `labelAlt`를 함께 넣어야 한다. 섹션 제목은 평문만 담는다. 채점도 답안에서 같은 구분자와 정수로 이루어진 `\frac` 하나를 받으므로, 표기를 바꾸어도 기존 평문 답안은 그대로 통한다.

## 초기 설치와 기존 DB 업그레이드

`20260914030000_database_content` migration이 기본 3개 수업(문항 15개), 진단 1개(문항 6개), 개념 3개를 한 번 등록한다. 수업 판본이 이미 있으면 내용, 해시, 발행 시각을 그대로 둔다. 이 migration은 당시 형식대로 판본을 JSON 문서로 심고, 뒤따르는 [저장 구조 migration](deployment.md#저장-구조-migration)이 그것을 행으로 옮긴 뒤 문서 칸을 지운다 — 새 DB에서도 `db:migrate` 한 번에 그 순서가 그대로 돈다. 기존 진단 실행과 과제 snapshot을 변경하지 않는다. 테이블 및 UTF-8 SQL 문자열 비교에 기존과 동일한 `utf8mb4_unicode_ci`를 명시한다.

배포는 `db:migrate → db:seed → content:publish → content:verify` 순서다. **`db:seed`는 플랫폼의 기본 콘텐츠를 심는 진짜 씨앗이다**(2026-09-17부터). `prisma/seed/fractions.json`의 분수 코스·수업 3개·진단 1개·개념 7개와 공통 사전 v3의 추가 개념 3개·뜻풀이 10개를 같은 `importContent` 경로로 설치한다. 이미 있는 판본은 변경하지 않고, 뜻풀이는 없는 항목만 설치한다. 검토한 기존 사전 변경은 `content:publish`가 적용한다. 판형이 바뀐 migration이 콘텐츠 표를 비운 뒤에는 이 명령이 콘텐츠를 다시 채운다. 이 파일에는 정답이 들어 있다 — 처음 콘텐츠를 심은 hex migration이 그랬듯, 플랫폼 기본 콘텐츠는 저장소가 원본이다. 테스트 fixture도 같은 파일을 읽는다. migration SQL 안의 초기 데이터는 역사적 이전 자료이며 운영 콘텐츠를 수정하는 곳이 아니다.

## 저장소 번들의 발행

`content/`의 JSON은 검토를 마친 **정답이 없는** 번들이다. 배포용 migrator 이미지가 이 디렉터리를 함께 담고, 기동 전에 `content:publish`로 파일 이름 순서대로 발행한다. 새 용어나 개념을 추가하려면 파일을 고쳐 머지하면 되고, 서버에서 따로 명령을 실행하지 않는다.

적용 여부는 migration과 같은 방식으로 판단한다. `AppliedContentBundle`이 파일 이름과 내용 checksum, 적용 시각을 보관하고, checksum이 같으면 DB 작업 없이 건너뛴다. 파일이 바뀌었을 때만 등록을 시도하며, 원장 기록은 등록과 같은 transaction에서 쓰므로 내용이 들어가지 않으면 적용으로 남지 않는다.

이미 발행한 `versionId`의 내용을 고쳐 커밋하면 등록이 거부되어 배포가 실패한다. 판본 불변 규칙을 배포 단계에서 강제하는 것이다. 수정은 새 `versionId`를 파일에 추가한다. 문제집도 같다 — 번들의 `problemSets`는 `{ problemSetId, courseKey, name, versionId, problems }`이고, 발행된 판본의 문제는 바꿀 수 없으며 이름과 코스는 정체의 것이라 이름만 바꿀 수 있다.

```sh
npm run content:publish -- --dry-run
npm run content:publish
npm run content:publish -- --dir /secure/path/reviewed
```

정답·채점 규칙·힌트·해설이 들어가는 수업과 진단 번들은 이 디렉터리에 두지 않는다. 아래 수동 등록 경로를 쓴다. 예외는 플랫폼의 기본 콘텐츠 하나로, `prisma/seed/fractions.json`에서 `db:seed`가 심는다.

## 자유롭게 그리는 그림

`core.scene@1`은 정해진 도형이 아니라 **좌표 평면 위의 도형 목록**이다. 분수 막대로 그릴 수 없는 설명 그림은 이 블록으로 그린다.

```json
{
  "blockId": "fraction-meaning:s1:b5",
  "kind": "core.scene",
  "typeVersion": 1,
  "required": true,
  "payload": {
    "alt": "피자 한 판을 넷으로 나누고 세 조각에 색을 칠한 그림",
    "width": 320,
    "height": 200,
    "items": [
      { "kind": "ellipse", "cx": 160, "cy": 100, "rx": 80, "ry": 80, "fill": "fill-soft", "stroke": "ink", "strokeWidth": 1 },
      { "kind": "path", "d": "M 160 100 L 160 20 A 80 80 0 0 1 240 100 Z", "fill": "fill" },
      { "kind": "line", "x1": 250, "y1": 60, "x2": 210, "y2": 80, "stroke": "ink", "arrow": "end" },
      { "kind": "text", "x": 255, "y": 58, "text": "한 조각", "size": 13, "fill": "ink" }
    ]
  }
}
```

도형은 `rect`·`ellipse`·`line`·`polygon`·`path`·`text`·`strip` 일곱 가지이고, 한 그림에 최대 120개까지 넣는다. `path`는 SVG path 문법을 그대로 받으므로 사실상 어떤 모양이든 그릴 수 있다. `strip`은 분수 막대 하나를 도형으로 담은 것이라 다른 도형과 나란히 놓을 수 있다. 공통 속성은 `fill`·`stroke`·`strokeWidth`·`dash`·`opacity`·`rotate`다.

`width`·`height`는 그림이 화면에서 차지하는 크기 그대로다. 도면 1단위가 1 CSS 픽셀로 그려지므로 `size: 14`인 글자는 본문 14px과 같은 크기가 되고, 그림을 크게 하려면 `width`·`height`를 키운다(글자도 함께 커진다). 칸이 도면보다 좁으면 그림 전체가 같은 비율로 줄어들며, 편집 화면의 캔버스도 같은 규칙으로 그리므로 거기서 맞춘 크기가 그대로 나간다.

색은 앱 팔레트 이름(`ink`, `green`, `fill`, `fill-soft`, `sand`, `sky`, `line`, `paper`, `white`, `none` 등)이나 `#rrggbb` 표기만 받는다. 이름을 쓰면 테마에 맞는 CSS 변수로 그려진다.

**마크업이 아니라 데이터다.** 값은 전부 렌더러가 만든 요소의 속성으로만 들어가고, 문서에 저자의 마크업이 그대로 삽입되는 경로는 없다. `path`의 `d`는 명령과 숫자만 허용하고, 알 수 없는 색 이름은 그려지지 않는다. 그래서 그림의 자유도를 열어도 임의 SVG를 붙이는 것과 달리 안전하다. 같은 이유로, 나중에 AI가 도형을 만들어 주는 기능을 붙이더라도 **생성 결과를 이 스키마로 검증**한 뒤 그대로 저장하면 된다.

그림 전체의 이름은 `alt`가 평문으로 맡는다. 도형 하나하나는 낭독에서 제외되므로, 그림이 말하려는 바를 `alt` 한 문장에 담는다.

캡션과 `text` 도형에는 수식을 쓴다. `text`의 `text`에 `$\frac{3}{4}$`처럼 적으면 본문과 같은 KaTeX로 그려진다. **저장되는 값은 그래도 평문 문자열이다** — 본문이 저장하는 것과 같은 글자이고, 스키마도 길이 제한이 붙은 문자열 그대로다. 마크업이 되는 것은 렌더러 안에서뿐이며 수식 바깥 글자는 전부 이스케이프하므로, 위의 「마크업이 아니라 데이터다」는 그대로 성립한다. 저자가 쓰는 것은 TeX이지 마크업이 아니고, KaTeX는 `trust: false`로 부르므로 `\href`·`\url`·raw HTML에는 닿지 못한다.

### 움직이는 그림

`frames`를 넣으면 같은 그림이 여러 장면으로 이어진다. 장면은 **이미 있는 도형을 옮기고 감추고 색을 바꿀 뿐**이고, 도형을 새로 만들거나 지우지 못한다. 그래서 정지 그림으로 안전한 것은 움직여도 안전하다.

```json
{
  "alt": "조각 하나가 막대 옆으로 옮겨 붙는 장면",
  "width": 320, "height": 200,
  "items": [
    { "id": "bar", "kind": "strip", "x": 20, "y": 80, "width": 280, "height": 40, "parts": 4, "filled": 3 },
    { "id": "piece", "kind": "rect", "x": 20, "y": 150, "width": 65, "height": 40, "fill": "sand" }
  ],
  "frames": [
    { "changes": [], "caption": "조각이 아직 따로 있어요." },
    { "changes": [{ "id": "piece", "dx": 215, "dy": -70 }], "caption": "네 번째 칸에 꼭 맞아요." }
  ],
  "frameMs": 1200
}
```

도형에 `id`를 주면 장면이 그 도형을 가리킬 수 있다. 장면의 변화는 `dx`·`dy`(이동), `opacity`, `rotate`, `fill`, `hidden`이며, 없는 이름을 가리키거나 이름이 겹치면 발행을 거부한다. 장면은 2~12개, `frameMs`는 400~6000이고 `loop`·`autoplay`를 함께 쓸 수 있다. 재생·멈춤·앞뒤 버튼은 항상 함께 그리며 `autoplay`는 동작 줄이기 설정에 양보한다. 장면마다 캡션을 따로 달 수 있고, 그림 전체의 이름은 여전히 `alt` 하나다.

편집기에서는 「움직이게 만들기」를 누르고 장면을 고른 뒤 도형을 끌면 그 장면에서의 위치가 정해진다. 「기본」을 고르고 끌면 그림 자체가 움직인다.

### 직접 놓아 보는 그림

`zones`와 `task`를 넣으면 학습자가 도형을 끌어다 놓는 그림이 된다. 끌 수 있는 도형은 `draggable: true`와 함께 `id`·`label`을 갖고, 자리는 `accepts`로 어떤 도형을 받을지 정한다(비우면 무엇이든 받는다).

```json
{
  "alt": "조각 두 개를 알맞은 칸에 놓는 그림",
  "width": 320, "height": 200,
  "items": [
    { "id": "half", "label": "반쪽 조각", "draggable": true, "kind": "rect", "x": 20, "y": 150, "width": 60, "height": 34, "fill": "sand" }
  ],
  "zones": [
    { "id": "slot1", "label": "첫째 칸", "x": 120, "y": 40, "width": 70, "height": 40, "accepts": ["half"] }
  ],
  "task": { "prompt": "조각을 알맞은 칸에 놓아 보세요.", "successText": "딱 맞았어요." }
}
```

조작 방법은 세 가지가 같은 일을 한다. 마우스로 끌어다 놓기, 도형을 눌러 든 뒤 자리를 누르기, 키보드로 도형에 초점을 두고 Enter를 눌러 든 뒤 자리에서 Enter. 그래서 드래그가 안 되는 기기에서도 전부 할 수 있다. 자리 하나에는 도형 하나만 들어가고, 다른 도형을 넣으면 먼저 있던 것이 제자리로 돌아간다.

**채점하지 않는다.** 놓은 결과는 서버로 가지 않고 진도·학습 증거·개인화에 반영되지 않으며 단계 완료를 막지도 않는다. 그래서 문항 본문·힌트·해설과 용어 풀이에 이 그림을 넣으면 발행을 거부한다. 같은 이유로 **한 그림은 스스로 움직이거나(`frames`) 학습자가 옮기거나(`zones`) 둘 중 하나**이고, 둘을 같이 쓰면 거부한다.

발행 검증은 이것들도 함께 본다. 자리가 있는데 `task`가 없거나, `task`만 있고 자리가 없거나, 끌 수 있는 도형이 하나도 없거나, 끌 수 있는 도형에 `label`이 없거나, 자리가 받겠다고 적은 도형을 옮길 수 없으면 거부한다.

편집은 `/authoring`의 캔버스에서 한다. 도형을 추가하고 마우스로 끌어 옮기고, 모서리 손잡이로 크기를 바꾸고, 색·선·회전·앞뒤 순서를 패널에서 고친다. `path`의 좌표와 다각형의 꼭짓점은 텍스트로 직접 적을 수도 있다.

## 화면에서 편집하고 발행하기

`/authoring`은 수업을 준비하는 사람이 쓰는 화면이다. 발행된 수업의 다음 판본이나 아직 아무도 발행하지 않은 수업의 초안을 만들고, 학습 화면과 같은 렌더러가 그린 수업 위에서 고치고, 검증을 통과하면 발행한다. CLI와 같은 `importContent`를 호출하므로 검증·참조 검사·불변 규칙·트랜잭션이 모두 동일하다. 화면은 쓰기 경로를 하나 더 만드는 것이 아니라 같은 경로에 손잡이를 붙인 것이다.

### 누가 읽는 화면인가

수업을 준비하는 사람이 읽는 화면이므로, 기본 상태에서는 **블록 ID·판본 ID·`required`·대체 설명처럼 시스템이 쓰는 이름을 보여주지 않는다.** 판본은 「4판」으로 읽히고, 접힌 문항은 자기 이름 대신 지문의 첫 줄로 자신을 말하고, 개념은 키가 아니라 카탈로그가 부르는 이름으로 나온다.

서비스를 함께 운영하는 사람에게는 그 이름들이 필요하다. 화면 **발치의 전문가 모드**를 켜면 모두 돌아온다. 한 번 정하고 두는 계정 설정이라 머리말이 아니라 일이 끝나는 자리에 둔다. 이 설정은 계정에 남으므로(`User.editorExpertMode`) 브라우저를 옮겨도 따라온다. **보이는 것만 바꾼다** — 무엇을 쓰고 발행할 수 있는지는 전적으로 역할이 정하고, 두 상태에서 같다.

### 미리보기가 곧 편집기다

화면은 **단계 목록 · 수업 · 고른 것**의 세 칸이다. 가운데는 학습 화면과 **같은 렌더러**가 그린 그 수업이다 — 옆에 따로 미리보기가 없는 이유는 가운데가 미리보기이기 때문이다. 블록마다 그 위에 테두리만 씌워 고를 수 있게 했고(`ContentBlocks`의 `wrap`), 그래서 편집기가 두 번째 렌더러를 들고 학습 화면과 어긋날 여지가 없다.

제목과 글은 **그 자리에서 쓴다.** 수업 제목·단계 제목은 보이는 그대로의 글자에 타이핑하고, 문단은 고르면 같은 서체·크기·행간의 텍스트 상자가 된다. 고른 상태가 원문이고 그렇지 않으면 그려진 것이라, `$...$`와 `@` 용어 걸기가 그대로 살아 있다. 캐럿은 문단 끝에 놓인다 — 그려진 글자의 어느 지점이 원문의 어느 자리인지는 수식과 용어 연결을 지나면 계산할 수 없다.

그림·문제집처럼 폼이 필요한 블록은 **오른쪽에서 고친다.** 오른쪽은 **지금 고른 것 하나**만 답한다 — 문항이 있으면 문항, 없으면 블록, 그것도 없으면 그 단계(역할·복제·삭제)다. 본문에서 쓰는 문단처럼 오른쪽에 보여 줄 칸이 하나도 남지 않는 블록은 이름과 손잡이만 있는 한 줄로 줄어든다. 발행된 판본에서는 오른쪽 전체가 잠긴다.

**수업이 자신에 대해 말하는 것은 다른 화면이다.** 한 줄 소개·예상 시간·다루는 개념·먼저 알아야 하는 개념·마친 뒤 복습·이 수업의 뜻풀이, 그리고 초안 삭제는 머리말의 **「수업 정보」**에 모여 있다. 한 칸이 「이 수업은 무엇인가」와 「이 문단은 무엇인가」를 함께 답하면, 문단을 고치러 온 사람이 수업의 개념 목록을 지나야 문항의 힌트에 닿는다. 수업은 몇 번 정하고, 문단은 오후 내내 쓴다. 발행 검사가 거부한 자리가 수업 쪽이면 그 화면이 먼저 열린다 — 수업 제목만은 시트에 있으므로 예외다.

**개념은 목록이 아니라 검색으로 고른다.** 고른 개념만 칩으로 남고, 더할 것은 이름으로 찾는다. 개념은 서비스와 함께 늘어나므로, 전부 펼쳐 두는 목록은 함께 길어지는 목록이다.

### 편집과 해보기

머리말의 **편집 / 해보기**로 화면을 바꾼다. 해보기는 같은 수업을 **학습 화면의 문항 카드**(`features/learning/problem-card.tsx`)로 그린다 — 답 칸, 「정답 확인」, 힌트 버튼, 채점 문구까지 학습자가 만나는 그대로다. 골라서 고칠 손잡이는 전부 사라진다.

채점은 **서버가 한다.** 편집기도 정답을 알고 있지만, 여기서 채점하면 학습 API의 채점기와 따로 노는 두 번째 채점기가 생긴다. `draft.tryAnswer`는 초안이 가진 문항을 `gradeAnswer`로 판정하고, `draft.openHint`는 그 문항의 힌트를 돌려준다. 그래서 저장되지 않은 변경이 있으면 해보기로 넘어갈 때 **먼저 저장한다** — 서버가 가진 것이 채점되는 것이기 때문이다.

**아무것도 기록되지 않는다.** 시도·힌트 사용·진도 어느 것도 쓰지 않는다. 문항을 쓰고 있는 계정의 풀이가 학습 증거가 되면, 답한 적 없는 사람에 대한 근거가 된다. 해설은 학습자에게 보여 주지 않으므로(`solutions: 'not-exposed'`) 해보기에도 나오지 않고 「편집」에서 쓴다.

### 문항 편집

문항은 **수업 화면에서 직접 고른다.** 문항도 블록처럼 그 자리에 테두리가 생기고, 누르면 지문은 거기서 바로 쓰고 오른쪽에는 지문이 보여 주지 않는 것들 — **정답·다루는 개념·힌트·해설** — 이 열린다. 해설은 학습 화면이 아직 보여 주지 않으므로 개수만 말하는 접힌 칸이다. 「문제집」 블록을 고르면 그 활동이 가진 문항의 목록이 나오고, 거기서 순서를 바꾸고 더하고 복제하고 뺀다. 힌트·해설은 수업 본문과 같은 블록 카드를 쓰므로 그림이나 뜻풀이도 문항 안에 넣을 수 있다. 문제집 안에 또 문제집을 넣는 것만 막혀 있다.

**문제집은 그 자리에서 생긴다.** 단계에 「문제」 블록을 더하면 편집기가 이름 없는 문제집을 하나 만들고(`ps-…` ID), 저장할 때 서버가 수업의 코스에 그 정체를 쓴다. 작성자는 「문제집」이라는 말을 만나지 않는다. 활동이 가진 문항이 그 문제집의 **마지막 발행 판본과 같으면** 블록은 그 판본을 참조하고 아무것도 새로 만들지 않는다. 다르면 문제집의 **다음 판본이 초안**(`ContentDraft`, `ownerKind='problem_set'`)으로 생겨 수업과 함께 발행된다. 문항을 원래대로 되돌리면 초안도 사라진다. 이름 있는 문제집을 가져다 쓰거나 이름을 주는 화면은 아직 없다.

**활동을 지우면 그 문항도 함께 간다.** 한 문항은 한 활동에만 속하므로, 활동만 지우면 아무것도 가지지 않은 문항이 남는다. 편집 화면은 그런 문항을 저장하지 않고 걷어낸다(`dropLooseProblems`). 단계를 지울 때도 같다. **별도로 발행된 복습 풀(`review`)은 그대로 유지할 수 있다.** 「수업 정보」에서 복습을 끄거나 수업 안의 문제 활동을 복습 대상으로 선택할 수도 있다. 활동을 선택하면 저장 시 정규화된 문제집 판본·문항 ID를 복습 참조에도 반영한다. 선택한 활동을 삭제하면 복습도 해제되며 되돌리기로 함께 복구된다.

**복제는 단계·블록·문항 어디서나 된다.** 사본은 원본 바로 뒤에 놓이고, 문서가 한 번만 부르는 이름은 전부 새로 받는다. 활동을 복제하면 **그 활동이 가진 문항까지 복제된다** — 한 문항은 한 활동에만 속하므로 두 활동이 같은 문항을 가리킬 수 없다. 단계를 복제하면 그 안의 블록과 활동의 문항까지 모두 새 이름을 받는다.

정답은 **숫자**로 적고, 답안 형식을 「정수만 / 숫자(정수·소수·분수)」에서 고른다. 숫자 형식에서는 `3`, `3.0`, `6/2`처럼 값이 같은 답을 인정한다. 답안 형식과 기약분수 제약은 정답 칸 아래 **「답 인정 범위 바꾸기」**에 접혀 있고, 지금 무엇을 인정하는지는 정답 칸 밑에 한 줄로 적힌다. 새 문항은 정수 정답으로 시작하며, 문자식·좌표쌍·증명의 자동 채점은 지원하지 않는다. 정답 원문은 문항별로 보관하여 문항 전환·되돌리기 때 다른 문제의 답이 표시되지 않으며, 잘못된 입력이 하나라도 있으면 저장·검증·발행을 막고 해당 문항으로 안내한다. 응답 형식(`responseSpec`)과 힌트 유무(`hintAvailable`)는 서버에서 정답·힌트로부터 유도한다.

**문항도 불변이다.** 이미 발행된 판본이 가진 문항의 내용을 고치면 저장할 때 **새 `problemVersionId`** 가 만들어지고, 그 문항을 가리키던 활동과 숙제 참조가 함께 옮겨간다. 이름은 판본을 따라간다 — `practice-1:v1`을 `:v2` 초안에서 고치면 `practice-1:v2`가 된다. 아직 발행된 적 없는 문항(같은 초안에서 방금 쓴 것)은 이름이 그대로다. 학습자의 풀이·힌트 기록과 과제 snapshot이 모두 이 이름을 가리키므로, 한 번 답이 제출된 이름이 다른 문항을 뜻하게 둘 수는 없다.

문항을 빼면 **쓰고 있는 판본에서만** 빠진다. 이미 발행된 판본은 자기가 발행될 때의 문항을 그대로 가지고 있다.

초안은 기준 판본의 문서를 복사해 만든다. 문항을 쓴다는 것은 정답을 쓴다는 것이므로, **정답·힌트·해설은 콘텐츠 역할을 가진 계정에만 내려간다.** 학습 API는 예전과 같이 학습자에게 공개 절반만 보낸다.

### 개념과 뜻풀이 편집

뜻풀이도 화면에서 쓴다. 상단 **「뜻풀이 사전」** 탭 또는 **「수업 정보」의 「뜻풀이 관리」** 에서 범위를 **공통 사전 / 수업 뜻풀이** 중에 고르고, 범위를 바꾸면 뜻풀이를 자동으로 불러온다. 이전 범위의 목록은 즉시 비우고 늦게 도착한 응답은 버린다. 범위를 바꾸거나 저장하면 스스로 다시 읽으므로 새로고침 단추는 없고, 불러오지 못했을 때만 오류 배너가 「다시 불러오기」를 준다. 본문만 있고 한 줄 설명이 없는 뜻풀이는 목록에서 그렇다고 말한다. 아직 발행하지 않은 수업도 선택할 수 있으며, 편집 중에는 저장하거나 닫은 뒤 범위를 바꾼다. 미리보기와 해보기는 뜻풀이 본문을 공유 렌더러에 전달한다. 공통 사전은 관리자만, 수업 뜻풀이는 콘텐츠 역할이 있으면 쓸 수 있다 — 수업의 뜻풀이를 쓰는 것은 그 수업을 쓰는 일의 일부이기 때문이다.

**뜻풀이는 판본이 없고 초안도 없다.** 저장이 곧 최신이고, 그 뜻풀이를 건 모든 수업에 바로 반영된다. 어떤 판정에도 쓰이지 않으므로(힌트로 기록하지 않고 개인화에 쓰지 않는다) 되찾을 과거가 없다. 수업은 개념을 키로 걸므로 문구를 고치는 데 수업을 다시 발행할 필요가 없다.

뜻풀이는 개념 하나를 설명한다. 있는 개념을 고르거나, 아직 없는 개념이면 **이름을 적고 자동 생성된 키로** 뜻풀이와 함께 만든다. 그렇게 생긴 개념도 `assessable=true`로 생성되어 수업과 문제에서 선택할 수 있다. 「분수의 의미」 같은 수업 제목 대신 「분수·분자·분모」처럼 작은 단위로 이름을 붙인다. **「개념으로 찾기」**에서는 개념 하나의 뜻풀이와 관련 수업을 함께 확인한다. 중복 개념을 하나로 합치는 화면은 아직 없다. 이 범위에서 부르는 이름(`label`)은 비워 두면 개념의 이름을 그대로 쓴다 — 「통분」을 한 수업에서만 「분모 맞추기」라고 부르고 싶을 때 적는다. 설명 블록의 ID는 범위·개념을 따라 서버가 붙이므로 작성자가 고를 일이 없다.

발행은 CLI와 같은 `importContent`를 지나므로, 없는 개념을 가리키거나 발행된 수업이 건 뜻풀이의 본문을 비우는 저장은 여기서도 같은 이유로 거부된다.

뜻풀이의 글에서도 `@`로 다른 개념을 연결한다. 공통 사전은 공통 사전만, 수업 뜻풀이는 공통 사전과 같은 수업 뜻풀이를 참조한다. 없는 본문·잘못된 범위는 저장 시 거부하며 순환 참조는 허용한다. 문제집과 놓아 보는 그림은 넣을 수 없다. 학습자 미리보기에서 연결을 따라가며 설명의 맥락과 순환을 확인한다.

### 코스에서 수업 준비하기

첫 화면은 코스 목록이며 검토 요청·최근 수정 초안을 함께 보여 준다. 코스를 열면 수업 순서, 발행 상태와 작성 중인 초안을 볼 수 있다. 기존 초안은 이어 열고, 없으면 「수정 시작」으로 다음 판을 만든다. 관리자만 코스를 만들거나 이름·소개를 고치고 수업 순서를 바꿀 수 있다(`course.save`, `course.reorder`). 코스 변경은 즉시 반영되며 수업 판본을 다시 발행하지 않는다. 순서 변경은 해당 코스의 전체 수업 키를 중복 없이 받아 트랜잭션에서 검사·저장한다. 편집 권한 관리는 별도 탭에 있다.

### 새 수업 시작하기

**새 수업은 화면에서 시작한다.** 발행된 판본이 없는 수업 키로 초안을 하나 만든다(`lesson.create`). 일반 모드에서는 코스 안에서 이름과 개념만 고르면 키를 자동으로 만들며, 전문가 모드에서만 키를 직접 고친다. 키는 이 수업 안의 모든 이름이 만들어지는 바탕이라 영문 소문자·숫자·하이픈만 쓰고, 한 번 발행하면 옮길 수 없다. 이미 발행됐거나 초안이 있는 키는 거부한다. 처음 상태는 **설명 한 단계와 연습 한 단계(문항 하나)** 인데, 발행 스키마가 문항 없는 수업을 거부하므로 시작부터 유효하지 않은 문서를 주지 않기 위해서다.

**수업이 가르치는 개념도 화면에서 고친다.** `DraftMeta.conceptKeys`로 초안이 실어 나르고, 편집 화면의 「이 수업」에서 고른다. 하나 이상이어야 하고(발행 스키마), 평가할 수 있는 개념(`assessable`)만 고를 수 있으며, 문항이 고를 수 있는 개념은 여기서 고른 것뿐이다.

선행 개념은 「수업 정보」의 「먼저 알아야 하는 개념」에서 고른다(`DraftMeta.prerequisiteConceptKeys`). 가르치는 개념을 바꾸면 그 개념은 선행 목록에서 제외한다. 새 수업에서 개념을 검색할 수 있고, 관리자는 없는 학습 개념을 평가 가능한 개념으로 새로 만들 수 있다(`concept.create`). 기존 개념의 평가 여부 변경과 중복 병합은 이 기능에 포함되지 않는다.

### 절차

1. 코스를 열어 기존 초안을 이어 쓰거나, **수정 시작** 또는 **수업 추가**로 시작한다. 판본 ID는 `lessonKey:v{다음 번호}`로 제안된다. 전문가 모드에서는 직접 고칠 수 있다.
2. 단계를 고르고 수업 위에서 고친다. 쓰는 동안 화면이 스스로 저장하고, 지운 것은 `⌘Z`나 알림의 「되돌리기」로 되찾는다.
3. **해보기**로 학습자가 만날 화면을 한 번 지나 본다.
4. **발행 전 검사**. 검사는 발행과 같은 dry run이라 참조 오류·중복 ID·낭독용 이름 누락까지 여기서 드러난다. 고칠 곳은 **그것이 있는 자리에** 나온다 — 해당 블록·문항에 테두리가 생기고, 고른 상태에서 오른쪽에 무엇이 거부됐는지 보인다. 아래 목록의 각 줄은 그 자리로 가는 길이다.
5. 작성자는 **검토 요청**으로 넘기고, 발행은 관리자가 한다.
6. **발행**. 되돌릴 수 없으므로 확인 단계를 한 번 거친다. 발행하면 `LessonVersion` 행이 새로 생기고 초안은 잠긴다.

쓰는 동안 화면이 스스로 저장하므로 상시 단추는 **발행 전 검사**와, 발행할 수 있으면 **발행**·아니면 **검토 요청**뿐이다. 저장에 실패했을 때만 「다시 저장」이 나온다. 초안을 버리는 것은 「수업 정보」 맨 아래에 있고, 발행과 같은 화면 안 확인을 거친다 — 되돌릴 수 없는 쪽이 더 허술한 창을 빌려 쓰지 않는다.

작성 중인 초안은 틀린 상태로도 저장된다. 검증을 통과해야 발행 버튼이 열리고, 이미 발행된 판본 ID로 발행하면 CLI와 같은 불변 오류로 거부한다. 발행한 초안은 더 고칠 수 없고, 다음 수정은 새 초안으로 만든다.

기존 수강자는 시작한 판본을 그대로 유지한다. 새 판본은 새로 수강하는 사람부터 보인다. 새 종류의 블록을 넣었다면 그 블록을 아는 앱이 먼저 배포되어 있어야 한다.

### 고칠 곳은 자리와 함께 온다

발행 규칙은 영어로 말한다 — import 명령이 쓰는 그 규칙이고, 화면에서 다시 쓰면 한 거부에 설명이 두 개가 된다. 대신 **어디인지는 서버가 이름으로 바꿔 보낸다.** `sections.2.contentBlocks.0` 같은 위치는 초안을 쓰는 동안 계속 움직이므로, `DraftIssue`는 `sectionId`·`blockId`·`problemVersionId`·`field`를 담아 나간다. 경로가 없는 참조 규칙(`Missing term: ... (blockId)`)은 규칙이 **이름을 대며 거부한 것**으로 자리를 찾는다.

블록 payload의 거부는 이제 **필드마다 따로** 올라온다(`core/content.ts`). 전에는 하나의 이슈에 zod 오류 전체가 JSON 덩어리로 들어가 경로가 `payload`에서 멈췄다 — 어느 칸이 틀렸는지도, 무엇이 틀렸는지도 한눈에 읽히지 않았다. 지금은 경로가 `payload.text`까지 가고, 편집 화면은 그 칸을 블록의 폼이 부르는 이름(「글」)으로 부른다.

### 다 썼다고 말하기

작성자는 발행하지 않는다. 대신 **검토 요청**으로 초안을 넘긴다(`draft.review`). 초안의 `status`가 `review`가 되고, 관리자의 초안 목록에 「검토 요청」으로 뜬다. 관리자는 발행하거나 「작성자에게 돌려보내기」로 되돌린다.

**검토 요청은 아무것도 잠그지 않는다.** 봐 달라고 부탁한 것이 고칠 수 없게 되는 이유는 아니므로, 요청한 뒤에도 작성자는 계속 고칠 수 있다. 상태는 관리자가 되돌리거나 작성자가 거둘 때만 바뀐다.

### 권한

편집 권한은 **계정이 가진 역할**이다. 운영자 한 사람을 가정하지 않으므로, 이후 교사 시스템이 붙으면 같은 역할을 그 사람들에게 부여하면 된다.

| 역할 | 할 수 있는 일 |
|---|---|
| `admin` | 모든 초안 열람·편집·삭제, 발행 |
| `author` | 자기 초안 작성·편집·삭제, 검증. 발행은 못 함 |
| 없음 | 화면이 열리지 않음. 목록도 내려주지 않음 |

역할이 없으면 API가 403을 돌려주고 초안·수업 목록을 아예 내려보내지 않는다. 아무에게도 역할을 주지 않은 배포에서는 이 화면이 누구에게도 열리지 않는다.

역할을 나눠 주는 일도 화면에서 한다. 초안 목록 아래 **「편집 권한」** 에서 관리자는 지금 권한을 가진 계정을 보고, 이름으로 계정을 찾아 `admin`/`author`를 주고 거둔다. `ContentAuthor` 행을 쓰는 것이라 **바로 반영되고 앱을 다시 띄울 필요가 없다.**

권한을 잃게 하는 조작에는 관문이 둘 있다. **자기 관리자 역할은 스스로 내려놓을 수 없고**, **마지막 관리자 행은 거둘 수도 `author`로 낮출 수도 없다.** 역할을 낮추는 것과 거두는 것은 같은 상실이므로 같은 관문을 지난다. 앞의 것만으로도 관리자가 0명이 되는 일은 막히지만, 뒤의 것은 환경 변수로 지정된 관리자가 배포와 함께 사라질 마지막 행을 없애는 경우를 위한 것이다.

- 첫 관리자는 `CONTENT_ADMIN_SUBJECTS` 환경 변수에 Google `sub`를 쉼표로 나열해 지정한다. 아직 아무 행도 없는 새 배포에 권한을 줄 사람이 최소 한 명 있어야 하기 때문이다. **부트스트랩 전용**이며, 그 계정으로 화면에서 자신을 포함해 역할을 나눠 준 뒤에는 변수를 비워도 된다.
- 환경 변수로 지정된 관리자는 행이 아니므로 화면이 「배포 설정」으로 표시만 하고 거두지 않는다. 그 역할은 배포를 고쳐야 바뀐다.
- 공용 `open-authoring` 계정에는 역할을 줄 수 없다. 아무도 로그인하지 않아서 생긴 계정이지 권한을 맡길 사람이 아니다.
- 계정 찾기는 표시 이름의 일부로 찾는다. 교사 권한 모델이 생기면 같은 행을 쓰거나 같은 함수에 조직 규칙을 더하면 되고, 화면과 API는 고치지 않는다.

### 로그인 없이 여는 스위치

`CONTENT_OPEN_ACCESS=true`면 `/authoring`이 로그인도 역할도 없이 열리고, 방문자는 공용 `open-authoring` 계정으로 편집·발행한다. 아직 사용자가 없는 배포에서 혼자 콘텐츠를 만들 때를 위한 스위치다.

이것은 접근 제어가 아니다. 켜져 있는 동안에는 **경로를 알아낸 누구든 발행·삭제하고 미발행 초안을 읽을 수 있다.** 주소를 아무에게도 알리지 않았다는 것은 추측 난이도이지 권한 검사가 아니므로, 서비스를 공개하기 전에 끄고 역할 기반 권한으로 돌아간다. 기본값은 꺼짐이고, 켜진 상태에서 첫 요청이 오면 서버 로그에 `content_authoring_open`을 한 번 남긴다. 켜고 끄는 것은 그때까지의 발행 기록에 영향을 주지 않는다.

### 아직 화면에 없는 것

**진단 편집**은 아직 CLI 경로를 쓰고, **조직·코스 범위의 용어**도 모델에는 있지만 화면에는 없다. **일반 이미지**를 올리는 길도 없어서 그림은 도형으로 그린다. 판본끼리 무엇이 달라졌는지 견주어 보는 화면도 없다.

**별도 복습 문제집의 본문 편집은 아직 CLI 경로다.** 화면에서는 기존 복습을 유지·해제하거나 수업 안의 문제 활동으로 교체할 수 있다. 기존 별도 문제집의 본문 자체를 고치려면 `content:export` → 편집 → `content:import`를 쓴다. 이름 있는 문제집을 여러 수업이 가져다 쓰는 것과 「전부 고치기 / 이 수업만 따로 두기」도 화면에 없다.

**문단을 고를 때 캐럿은 끝에 놓인다.** 그려진 글자의 어느 지점이 원문의 어느 자리인지는 수식과 용어 연결을 지나면 계산할 수 없어서, 틀린 자리에 놓는 것보다 끝을 택했다. 문단 중간을 고치려면 한 번 더 클릭한다.

**편집 화면에는 렌더 테스트가 없다.** 이 저장소의 vitest는 node 전용 순수 검사이므로, 화면을 검사로 묶으려면 `@testing-library/react` 도입이 따로 필요하다. 지금은 데이터 계층과 서버 규칙만 검사가 지킨다.

## 콘텐츠 내보내기·등록

검토된 DB 접속 환경의 서버/관리자 터미널에서 실행한다. `DATABASE_URL`은 해당 DB로 설정한다. 명령은 지정된 DB를 대상으로 하며 운영용 비밀값은 셸 기록이나 저장소에 적지 않는다.

```sh
npm run content:verify
npm run content:export -- --out /secure/path/content-export.json
npm run content:import -- --file /secure/path/reviewed-content.json --dry-run
npm run content:import -- --file /secure/path/reviewed-content.json
npm run content:verify
```

내보내기에는 정답·채점 규칙·힌트·해설이 포함된다. 파일은 `0600` 권한으로 새로 만들며 기존 파일을 덮어쓰지 않는다. 공개 API나 모바일 번들에 포함하지 않는다. 등록·검증 결과는 개수만 출력한다. 웹 사용자에게 등록 API를 제공하지 않는다.

번들 형식은 아래와 같다. 내보낸 파일을 복사해 편집하면 각 문서의 전체 형식을 확인할 수 있다.

```json
{
  "schemaVersion": 1,
  "courses": [],
  "concepts": [],
  "lessons": [],
  "problemSets": [],
  "diagnostics": [],
  "definitions": []
}
```

`courses`·`problemSets`·`definitions`는 나중에 추가한 항목이라 생략할 수 있다. 진단은 `problemSet: { problemSetId, problemSetVersionId, problemVersionIds }`로 문제집 판본을 참조하고, 문항은 `problemSets`에 있다.

필요한 항목만 넣는 부분 등록도 지원한다. 예를 들어 기존 개념을 참조하는 새 수업만 넣고 `concepts`와 `diagnostics`는 빈 배열로 두어도 된다. 개념 키는 기존 DB 또는 같은 번들에 반드시 있어야 한다. 파일 크기는 최대 5 MiB이며 큰 번들은 나누어 등록한다.

발행한 수업/진단은 덮어쓰지 않는다. 수정하려면 `versionId`를 새로 부여한다. 내용이 바뀐 문항도 `problemVersionId`를 새로 부여하고, 그 문항을 든 문제집도 새 판본이 되며, 단계·복습 풀·진단의 참조를 함께 바꾼다. 수업·문제집·진단의 같은 판본 ID에 동일 내용을 재등록하면 기존 판본을 변경하지 않는다. 개념(`Concept`)은 같은 키로 이름·평가 여부를, 문제집은 같은 ID로 이름을, 코스는 같은 키로 제목·요약·수업 순서를 갱신할 수 있고 뜻풀이는 그 자리에서 다시 쓴다. MySQL이 JSON 객체 키 순서를 바꾸어도 의미가 같으면 동일한 내용으로 판단한다. 기존 해시는 다시 계산하지 않으며 새 판본 해시는 정렬된 JSON 키를 기준으로 계산한다.

새 수업/진단 판본은 번들 배열 순서대로 발행된다. 같은 lessonKey/diagnosticKey를 가진 새 판본 중 마지막 항목이 최신이 된다. 내보내기도 발행 순서로 제공한다. 이미 있는 판본 재등록은 최신 판본을 되돌리지 않는다. 이전 내용으로 되돌리고 싶다면 새 판본 ID로 재발행한다.

등록 전 전체 참조와 문서 형식을 검사한다. 알 수 없는 필수 블록, 중복 ID, 없는 개념, 바뀐 기존 판본, 기존 문제 ID의 다른 내용, 두 문제집에 든 문제 ID, 수업·진단이 가리키는 문제집 판본이 없거나 그 판본에 없는 문제이거나 다른 코스의 문제집인 참조, 수식 `label`에 빠진 `labelAlt`, 수식 표기가 섞인 낭독용 이름은 거부한다. 용어에서는 없는 참조, 없는 `skillKey`, 판본마다 달라지는 용어의 개념(범위별로 센다), 본문에 없는 표층 문자열, 자신이 평가하는 개념을 문항 안에서 설명하는 주석, 다른 수업이 가진 용어를 가리키는 참조, 범위를 적고도 어디 것인지 밝히지 않은 용어를 거부한다. 쓰기는 한 DB 트랜잭션으로 처리하며 `--dry-run`은 쓰지 않는다.

## 뜻풀이 걸기

본문에서 낱말에 개념의 뜻풀이를 걸려면 `core.rich_text@3` 블록을 쓴다. 편집기에는 이 블록이 따로 있지 않다 — 수업·문항·뜻풀이 팔레트의 **「글」이 곧 이것**이다. 기존 뜻풀이의 `@1` 글은 편집할 때 `@3`으로 전환한다. 어느 스키마 판을 쓸지는 블록이 놓이는 자리가 정하므로 아무도 고르지 않는다. (`@2`는 옛 용어 키를 걸던 판이고, 2026-09-17의 migration이 발행된 블록을 모두 `@3`으로 옮겼다.)

글을 쓰다가 **`@` 뒤에 이름을 적으면** 걸 수 있는 뜻풀이가 떠오르고, 고르면 그 이름이 글에 들어가면서 연결이 함께 적힌다. 같은 낱말이 여러 번 나올 때 **몇 번째인지는 적은 자리가 정한다** — 작성자가 세지 않는다. 한 블록에 한 개념은 한 번만 걸 수 있으므로, 같은 개념을 다시 고르면 연결이 그 자리로 옮겨간다. 걸린 낱말은 글 아래에 남고 거기서 뗄 수 있다. 키와 몇 번째까지 손으로 고치는 표는 전문가 모드에서만 나온다. 고를 수 있는 것은 공통 사전과 그 수업이 가진 뜻풀이 중 **본문이 있는 것**뿐이다. 뜻풀이의 글은 본문에 넣지 않고 `ConceptDefinition`을 참조한다. 뜻풀이를 고칠 때 그 개념을 건 수업을 모두 재발행하지 않기 위해서다.

### 뜻풀이를 가진 범위

개념은 전역이지만 **호칭과 뜻풀이는 범위마다 따로** 있다. 같은 개념이라도 범위가 다르면 다르게 불리고 다르게 설명될 수 있으나, 가리키는 개념은 같다. 설명 범위는 명시적으로 선택하며 학교급이나 준비도에 따라 자동으로 교체하지 않는다. 추상화 수준이 다른 수업까지 준비도를 이전할지는 별도 정책이다.

| 범위 | 누가 쓰나 | 지금 |
|---|---|---|
| `global` | 운영자. 수학 사전에서 모은 공통 뜻풀이 | 쓰고 있다 |
| `organization` | 학원 같은 조직 | 자리만 있다 |
| `course` | 코스 | 자리만 있다 |
| `lesson` | 그 수업의 작성자 | 쓰고 있다 |

**본문이 뜻풀이를 가리킬 때 범위까지 적는다.** 연결은 `{ conceptKey, surface, scopeKind?, scopeKey?, occurrence? }`이고, 범위를 적지 않으면 공통 사전을 뜻한다. 읽는 쪽이 「이 문항이 어느 수업·조직의 것인가」를 몰라도 뜻풀이를 찾을 수 있어야 하기 때문이다 — 과제는 여러 수업의 문항을 섞어 담으므로, 읽는 시점에는 그 맥락이 없다.

편집 화면에서는 「어디 뜻풀이」를 **공통 사전 / 이 수업** 중에서 고른다. `scopeKey`(어느 수업인지)는 블록이 들어 있는 문서에서 따라오므로 저장할 때 서버가 채운다. 그래서 **한 수업은 자기 뜻풀이만 가리킬 수 있고**, 다른 수업의 뜻풀이를 참조하면 발행이 거부된다.

```json
{
  "blockId": "fraction-addition:s1:b1",
  "kind": "core.rich_text",
  "typeVersion": 3,
  "required": true,
  "payload": {
    "text": "분모가 다르면 동치분수로 바꾸어 분모를 같게 만들어요.",
    "definitions": [
      { "conceptKey": "denominator", "surface": "분모" },
      { "conceptKey": "equivalent-fraction", "surface": "동치분수" }
    ]
  }
}
```

`surface`는 본문에 실제로 있는 문자열이고, 같은 말이 여러 번 나오면 `occurrence`로 몇 번째를 가리킬지 정한다(기본값 1). 수식 구간 안의 글자는 세지도, 표시하지도 않는다. 조사가 붙은 "분모를"에서도 `surface`가 "분모"면 그 부분만 표시한다.

**보여줄지는 수업을 쓴 사람이 정한다.** 어떤 낱말에 뜻풀이를 걸었다는 것이 곧 「여기서는 설명해도 된다」는 판단이므로, 서버는 학습자의 진도를 보고 그 판단을 뒤집지 않는다. 건 것은 전부 내려가고, 걸지 않은 낱말은 평문으로 남는다.

한때는 서버가 진도로 정했다 — 지금 배우는 수업이 가르치는 개념이나 과제가 평가하는 개념의 뜻풀이를 숨기고, 선수 개념과 앞 순서 수업의 것만 내려보냈다. 규칙이 옳게 도는지 확인하려면 수업 순서·선수 개념·과제 구성까지 머릿속에 들고 있어야 해서, 정작 글을 쓰는 사람이 결과를 예측하기 어려웠다. 그래서 규칙을 걷어내고 판단을 작성자에게 돌려주었다.

직접 연결에 남아 있는 평가 제약은 다음과 같다. **문항 안에서 그 문항이 평가하는 개념의 뜻풀이를 걸면 발행 단계에서 거부한다.** 이것은 진도가 아니라 답이 답 옆에 놓이는 문제라서 그대로 둔다. 같은 개념이라도 섹션 본문에서는 얼마든지 걸 수 있다.

수업의 설명·예시·정리에서는 뜻풀이 안의 개념을 같은 패널에서 따라 읽는다. 문제·힌트·해설·과제는 단일 단계 뜻풀이만 제공하며 서버 응답에서도 추가 연결을 제거한다. 지연 조회 API는 수업 판본과 출발점·연결 경로를 매 요청 검증한다. 진단 문항에는 뜻풀이를 제공하지 않는다. 이미 배운 개념 중 아직 연습이 필요한 것은 더 눈에 띄게 표시한다.

뜻풀이는 수업·진단과 달리 **얼리지 않는다.** 새로 조회할 때 현재 내용을 보여주고, **어느 개념인지는 연결을 쓸 때 정해진다**. 이미 시작한 수업과 배정된 과제의 문제집 판본에서도 마찬가지다. 열린 탐색의 뒤로 가기는 이미 받은 내용과 스크롤을 복원하며 재조회하지 않는다. 채점과 무관한 보조 설명이므로 정정이 즉시 반영되는 쪽을 택했다.

뜻풀이 열람은 힌트와 다르다. 도움받은 풀이로 기록하지 않으며 개인화 판단에도 사용하지 않는다.

### 기본 뜻풀이 등록과 기존 수업 연결

저장소의 `content/glossary-v3.json`은 기존 7개 개념에 정수·공약수·기약분수를 더하고 공통 뜻풀이 10개에 맥락과 개념 간 연결을 제공한다. 배포가 `content:publish`로 v2 다음 v3를 원장에 따라 한 번씩 등록한다. v2는 이미 적용한 파일이므로 수정하지 않는다. 최초 `db:seed`도 v3 사전을 설치하며 기존 뜻풀이의 편집은 덮어쓰지 않는다.

```sh
npm run content:import -- --file content/glossary-v3.json --dry-run
npm run content:import -- --file content/glossary-v3.json
```

기존 수업 본문에 연결을 다는 것은 별도 작업이다. 발행한 수업은 불변이므로 `content:export`로 내려받아 해당 `core.rich_text` 블록을 위 형식으로 바꾸고, `public.versionId`를 새로 부여해 등록한다. 문항을 바꾸지 않으면 `problemVersionId`는 그대로 재사용한다. 기존 수강자는 이전 판본을 유지하고 새로 수강하는 사람부터 연결본을 받는다. 내보낸 파일에는 정답이 들어 있으므로 저장소에 커밋하지 않는다.

2026-09-15에는 이 절차로 수식·용어 주석을 담은 v4 수업 3개를 발행했고, 이후 개념 스키마 migration에서 연결을 `core.rich_text@3`으로 옮겼다. 이는 이전 콘텐츠의 기록이다. #47의 실사용 전 초기화와 seed가 현재 v2 수업 3개를 새로 설치했으며, #48은 그 수업 판본을 바꾸지 않고 뜻풀이 연결과 사전 v3를 보강했다. 실행·초기화 범위는 [배포 문서](deployment.md#운영-콘텐츠데이터-작업-기록)를 따른다.

| `core.figure@1` | 발행된 판본이 계속 그려진다. 편집기에서 열어 고칠 수 있지만 새로 추가할 수는 없다. |
| `math.fraction_strip@1` | 위와 같다. |
| `math.fraction_sequence@1` | 완전히 제거했다. 발행된 콘텐츠가 없었다. 움직임은 `core.scene@1`의 `frames`로 만든다. |
| `math.fraction_builder@1` | 완전히 제거했다. 발행된 콘텐츠가 없었다. |

발행된 판본은 불변이라 고칠 수 없으므로, 이미 그 블록을 담은 수업이 있는 한 검증 스키마와 렌더러는 남긴다. 스키마를 지우면 그 판본을 수강 중인 사람의 수업이 열리지 않는다. 편집기 팔레트에서 빼는 것과 앱에서 지우는 것은 다른 일이다.

## 학습 중 콘텐츠가 추가되면

새로 수강하는 사람에게 최신 수업이 제공된다. 이미 수강한 사람은 시작했던 수업 판본을 유지한다. 배정된 과제와 저장한 답안도 그대로다. 시작점 확인의 안내·문항 수·예상 시간은 DB에서 읽고, 시작한 진단은 그때 복사한 문항으로 끝까지 이어간다. 진단 개편만으로 진행 중인 진단을 교체하지 않는다. 완료 후 재진단을 안내하는 별도 UX는 후속 범위다.

## 검증

`tests/definition-exploration.test.ts`는 같은 개념의 범위 구별, 순환, 조회 경로 위조·변경, 문제 응답의 링크 제거, 조회로 학습 기록을 쓰지 않는 것을 검사한다. `tests/authoring-integration.test.ts`는 설명 맥락과 작성자/관리자 권한도 확인한다.

`tests/content-store.test.ts`에서 MySQL 초기 데이터, 내보내기 재등록, dry run, DB만으로 새 수업·개념·진단 제공, 불변 판본·문항 보호, 과제와 진단 snapshot 보존을 검사한다. 뜻풀이는 없는 참조·잘못된 범위를 거부하고, 수업을 재발행하지 않고 설명을 고쳐 쓰는 경로를 검사한다. 범위가 생긴 뒤로는 같은 키를 가진 사전 용어와 수업 용어가 서로를 대신하지 않는 것, 각 범위의 참조가 정확한 뜻풀이를 가리키는 것, 다른 수업의 용어를 가리키면 거부하는 것도 같은 파일에서 본다.

편집 화면 쪽은 `tests/authoring.test.ts`(블록 폼·이름 짓기·정답 읽기·범위 채우기·복제·고아 문항·판과 지문의 표기)와 `tests/authoring-integration.test.ts`(MySQL에서 초안·문항 개명·역할 부여·용어 발행·새 수업·검토 요청·해보기 채점·거부의 자리)가 맡는다. 편집 기록(되돌리기)이 무엇을 한 걸음으로 묶는지는 `tests/edit-history.test.ts`가 순수 리듀서로 본다. `@`로 용어를 거는 계산은 `tests/term-mentions.test.ts`가 보고, 그 결과를 다시 `locateTerms`에 넣어 같은 자리를 가리키는지까지 확인한다. 본문 표시 위치 계산은 `tests/rich-text.test.ts`, 수업·과제 응답에 실제로 실리는 용어는 `tests/learning-integration.test.ts`에서 본다. 기존 채점·개인화·인증 테스트도 함께 실행한다. 코스 생성·권한·순서 검사, 선행 개념 저장, 복습 참조의 판본 변경과 미발행 수업의 뜻풀이 본문도 통합 검사에 포함한다.

**통합 검사는 `TEST_DATABASE_URL` 없이는 통째로 건너뛴다**(`describe.skipIf`). 서버나 스키마를 고쳤다면 그 변수를 준 상태로 실행하고 skipped 수를 함께 확인한다. #48 기준 전체 24개 파일·392개 테스트가 통과했다. 초기 설치와 해당 릴리스의 보존/초기화 범위는 [배포 기록](deployment.md#릴리스별-검증-기록)에 구분한다. 과거 릴리스의 보존 검증을 이후의 명시적인 콘텐츠 초기화까지 일반화하지 않는다. 이 검증은 수학 콘텐츠의 전문가 검수를 대신하지 않는다.


### 2026-09-17 편집 화면 정리

- 수업 단위 설정을 인스펙터에서 걷어내 **「수업 정보」** 화면으로 옮겼다(`features/authoring/lesson-settings.tsx`). 오른쪽 칸은 고른 것 하나만 답하고, 아무것도 고르지 않았으면 그 단계만 보여준다.
- 개념 선택이 체크박스 목록에서 칩과 검색으로 바뀌었다. 답안 형식·기약분수 제약과 해설은 접힌 칸이 되었고, 보여 줄 칸이 없는 블록 카드는 한 줄로 줄었다.
- 하단 상시 단추가 다섯에서 둘로 줄었다. 초안 삭제는 화면 안 확인으로 바뀌었고, 뜻풀이 사전의 새로고침 단추와 편집 화면의 이동 경로 표시를 없앴다. 전문가 모드는 화면 발치로 옮겼다.
- DB·서버 API·발행 규칙은 바뀌지 않았다. 화면의 배치와 이름만 바뀐다.

### 2026-09-17 콘텐츠와 편집 UI 정비

- 개념 7개에 공통 뜻풀이를 연결하고 기본 수업 3개를 다시 썼다. 수업·복습 문항 17개, 시작 진단 8문항이며 수업 본문은 `core.rich_text@3`와 `core.scene@1`을 쓴다. 분자·분모 등의 문항은 개별 개념에 연결한다.
