# DB 콘텐츠 관리

2026-09-14 · [DB 콘텐츠 전환 #6](https://github.com/team-campfire-dev/geunyang-math/pull/6) 운영 반영 완료. 릴리스별 검증은 [배포 기록](deployment.md#릴리스별-검증-기록)을 따른다.

기본 콘텐츠와 이후 발행한 콘텐츠의 운영 원본은 MySQL이다. 앱은 `ClassVersion`, `DiagnosticVersion`, `TermVersion`, `Skill`을 읽는다. 클래스·진단 문항·개념 이름을 TypeScript/JSON 파일에서 불러오는 런타임 경로는 없다.

## 저장 구조

- `ClassVersion.document`: 클래스 섹션, 콘텐츠 블록, 문항, 비공개 채점 규칙·힌트·해설, 숙제 문항 ID를 함께 보관하는 불변 JSON 문서.
- `DiagnosticVersion`: 진단 이름·설명·예상 시간·발행 시각과 불변 문항 JSON. `diagnosticKey=starting-point`의 최신 발행 판본을 새 진단에 사용한다.
- `TermVersion`: 용어 키, 용어가 속한 개념(`skillKey`), 표시 이름, 한 줄 요약, 설명 블록을 담은 불변 판본. 용어 키별 최신 발행 판본을 사용한다.
- `Skill`: 개념 키, 화면에 표시하는 이름, 표시 순서. 이름과 순서는 수정할 수 있다.
- `Enrollment.classVersionId`, `AssignmentItem.problemSnapshot`, `DiagnosticRun.document`: 수강·과제·진단의 기존 판본을 계속 참조하거나 복사해 보존한다.

JSON은 DB 안의 확장 가능한 블록 형식이다. `kind`, `typeVersion`, `payload`, `required`, `fallback` 계약은 유지한다. 기존 블록으로 만든 콘텐츠는 앱 재배포 없이 등록할 수 있다. 새로운 그래프·도형 블록 종류는 검증 스키마와 웹/모바일 렌더러를 추가한 뒤 배포해야 한다. 이번 변경은 편집 UI나 AI 생성기를 추가하지 않는다.

rich text는 `$...$`, `$$...$$`, `\(...\)` 안에 LaTeX를 담고, 도형 캡션은 한 줄로 표시하므로 인라인 형태만 쓴다. 수식 안에 한글을 넣으면 화면에 오류 표시가 나오므로 단위와 조사는 수식 밖에 둔다. 화면 낭독용 이름에는 수식 표기를 쓰지 않는다. `core.figure@1`은 `alt`가 그림 전체의 이름이고, `math.fraction_strip@1`은 수식 `label`을 쓸 때 평문 `labelAlt`를 함께 넣어야 한다. 섹션 제목은 평문만 담는다. 채점도 답안에서 같은 구분자와 정수로 이루어진 `\frac` 하나를 받으므로, 표기를 바꾸어도 기존 평문 답안은 그대로 통한다.

## 초기 설치와 기존 DB 업그레이드

`20260914030000_database_content` migration이 기본 3개 클래스(문항 15개), 진단 1개(문항 6개), 개념 3개를 한 번 등록한다. 클래스 판본이 이미 있으면 내용, 해시, 발행 시각을 그대로 둔다. 기존 진단 실행과 과제 snapshot을 변경하지 않는다. 테이블 및 UTF-8 SQL 문자열 비교에 기존과 동일한 `utf8mb4_unicode_ci`를 명시한다.

배포는 `db:migrate → content:publish → content:verify` 순서다. migration의 초기 데이터와 이미 적용한 번들은 다시 등록하지 않는다. `db:seed`는 이전 명령 호환용 읽기 전용 검증 별칭이다. migration SQL의 초기 데이터와 `tests/fixtures/initial-content.json`은 역사적 이전 자료·테스트 fixture이므로 운영 콘텐츠를 수정하는 곳이 아니다.

## 저장소 번들의 발행

`content/`의 JSON은 검토를 마친 **정답이 없는** 번들이다. 배포용 migrator 이미지가 이 디렉터리를 함께 담고, 기동 전에 `content:publish`로 파일 이름 순서대로 발행한다. 새 용어나 개념을 추가하려면 파일을 고쳐 머지하면 되고, 서버에서 따로 명령을 실행하지 않는다.

적용 여부는 migration과 같은 방식으로 판단한다. `AppliedContentBundle`이 파일 이름과 내용 checksum, 적용 시각을 보관하고, checksum이 같으면 DB 작업 없이 건너뛴다. 파일이 바뀌었을 때만 등록을 시도하며, 원장 기록은 등록과 같은 transaction에서 쓰므로 내용이 들어가지 않으면 적용으로 남지 않는다.

이미 발행한 `versionId`의 내용을 고쳐 커밋하면 등록이 거부되어 배포가 실패한다. 판본 불변 규칙을 배포 단계에서 강제하는 것이다. 수정은 새 `versionId`를 파일에 추가한다.

```sh
npm run content:publish -- --dry-run
npm run content:publish
npm run content:publish -- --dir /secure/path/reviewed
```

정답·채점 규칙·힌트·해설이 들어가는 클래스와 진단 번들은 이 디렉터리에 두지 않는다. 아래 수동 등록 경로를 쓴다.

## 자유롭게 그리는 그림

`core.scene@1`은 정해진 도형이 아니라 **좌표 평면 위의 도형 목록**이다. 분수 막대로 그릴 수 없는 설명 그림은 이 블록으로 그린다.

```json
{
  "blockId": "fraction-meaning:s1:b5",
  "kind": "core.scene",
  "typeVersion": 1,
  "required": true,
  "payload": {
    "alt": "피자 한 판을 넷으로 나누고 세 조각에 색을 칠한 그림",
    "width": 320,
    "height": 200,
    "items": [
      { "kind": "ellipse", "cx": 160, "cy": 100, "rx": 80, "ry": 80, "fill": "fill-soft", "stroke": "ink", "strokeWidth": 1 },
      { "kind": "path", "d": "M 160 100 L 160 20 A 80 80 0 0 1 240 100 Z", "fill": "fill" },
      { "kind": "line", "x1": 250, "y1": 60, "x2": 210, "y2": 80, "stroke": "ink", "arrow": "end" },
      { "kind": "text", "x": 255, "y": 58, "text": "한 조각", "size": 13, "fill": "ink" }
    ]
  }
}
```

도형은 `rect`·`ellipse`·`line`·`polygon`·`path`·`text`·`strip` 일곱 가지이고, 한 그림에 최대 120개까지 넣는다. `path`는 SVG path 문법을 그대로 받으므로 사실상 어떤 모양이든 그릴 수 있다. `strip`은 분수 막대 하나를 도형으로 담은 것이라 다른 도형과 나란히 놓을 수 있다. 공통 속성은 `fill`·`stroke`·`strokeWidth`·`dash`·`opacity`·`rotate`다.

색은 앱 팔레트 이름(`ink`, `green`, `fill`, `fill-soft`, `sand`, `sky`, `line`, `paper`, `white`, `none` 등)이나 `#rrggbb` 표기만 받는다. 이름을 쓰면 테마에 맞는 CSS 변수로 그려진다.

**마크업이 아니라 데이터다.** 값은 전부 렌더러가 만든 요소의 속성으로만 들어가고, 문서에 저자의 마크업이 그대로 삽입되는 경로는 없다. `path`의 `d`는 명령과 숫자만 허용하고, 알 수 없는 색 이름은 그려지지 않는다. 그래서 그림의 자유도를 열어도 임의 SVG를 붙이는 것과 달리 안전하다. 같은 이유로, 나중에 AI가 도형을 만들어 주는 기능을 붙이더라도 **생성 결과를 이 스키마로 검증**한 뒤 그대로 저장하면 된다.

그림 전체의 이름은 `alt`가 평문으로 맡는다. 도형 하나하나는 낭독에서 제외되므로, 그림이 말하려는 바를 `alt` 한 문장에 담는다. 캡션에는 수식을 써도 된다.

### 움직이는 그림

`frames`를 넣으면 같은 그림이 여러 장면으로 이어진다. 장면은 **이미 있는 도형을 옮기고 감추고 색을 바꿀 뿐**이고, 도형을 새로 만들거나 지우지 못한다. 그래서 정지 그림으로 안전한 것은 움직여도 안전하다.

```json
{
  "alt": "조각 하나가 막대 옆으로 옮겨 붙는 장면",
  "width": 320, "height": 200,
  "items": [
    { "id": "bar", "kind": "strip", "x": 20, "y": 80, "width": 280, "height": 40, "parts": 4, "filled": 3 },
    { "id": "piece", "kind": "rect", "x": 20, "y": 150, "width": 65, "height": 40, "fill": "sand" }
  ],
  "frames": [
    { "changes": [], "caption": "조각이 아직 따로 있어요." },
    { "changes": [{ "id": "piece", "dx": 215, "dy": -70 }], "caption": "네 번째 칸에 꼭 맞아요." }
  ],
  "frameMs": 1200
}
```

도형에 `id`를 주면 장면이 그 도형을 가리킬 수 있다. 장면의 변화는 `dx`·`dy`(이동), `opacity`, `rotate`, `fill`, `hidden`이며, 없는 이름을 가리키거나 이름이 겹치면 발행을 거부한다. 장면은 2~12개, `frameMs`는 400~6000이고 `loop`·`autoplay`를 함께 쓸 수 있다. 재생·멈춤·앞뒤 버튼은 항상 함께 그리며 `autoplay`는 동작 줄이기 설정에 양보한다. 장면마다 캡션을 따로 달 수 있고, 그림 전체의 이름은 여전히 `alt` 하나다.

편집기에서는 「움직이게 만들기」를 누르고 장면을 고른 뒤 도형을 끌면 그 장면에서의 위치가 정해진다. 「기본」을 고르고 끌면 그림 자체가 움직인다.

편집은 `/authoring`의 캔버스에서 한다. 도형을 추가하고 마우스로 끌어 옮기고, 모서리 손잡이로 크기를 바꾸고, 색·선·회전·앞뒤 순서를 패널에서 고친다. `path`의 좌표와 다각형의 꼭짓점은 텍스트로 직접 적을 수도 있다.

## 화면에서 편집하고 발행하기

`/authoring`은 발행된 클래스를 기준으로 다음 판본의 초안을 만들고, 블록을 폼으로 고치고, 학습 화면과 같은 렌더러로 미리 보고, 검증을 통과하면 발행하는 화면이다. CLI와 같은 `importContent`를 호출하므로 검증·참조 검사·불변 규칙·트랜잭션이 모두 동일하다. 화면은 쓰기 경로를 하나 더 만드는 것이 아니라 같은 경로에 손잡이를 붙인 것이다.

### 권한

편집 권한은 **계정이 가진 역할**이다. 운영자 한 사람을 가정하지 않으므로, 이후 교사 시스템이 붙으면 같은 역할을 그 사람들에게 부여하면 된다.

| 역할 | 할 수 있는 일 |
|---|---|
| `admin` | 모든 초안 열람·편집·삭제, 발행 |
| `author` | 자기 초안 작성·편집·삭제, 검증. 발행은 못 함 |
| 없음 | 화면이 열리지 않음. 목록도 내려주지 않음 |

역할이 없으면 API가 403을 돌려주고 초안·클래스 목록을 아예 내려보내지 않는다. 아무에게도 역할을 주지 않은 배포에서는 이 화면이 누구에게도 열리지 않는다.

- 첫 관리자는 `CONTENT_ADMIN_SUBJECTS` 환경 변수에 Google `sub`를 쉼표로 나열해 지정한다. 새 배포에 권한을 줄 사람이 최소 한 명 있어야 하기 때문이다.
- 나머지는 `ContentAuthor` 행(`userId`, `role`)으로 부여한다. 교사 권한 모델이 생기면 이 행을 쓰거나 같은 함수에 조직 규칙을 더하면 되고, 화면과 API는 고치지 않는다.

### 로그인 없이 여는 스위치

`CONTENT_OPEN_ACCESS=true`면 `/authoring`이 로그인도 역할도 없이 열리고, 방문자는 공용 `open-authoring` 계정으로 편집·발행한다. 아직 사용자가 없는 배포에서 혼자 콘텐츠를 만들 때를 위한 스위치다.

이것은 접근 제어가 아니다. 켜져 있는 동안에는 **경로를 알아낸 누구든 발행·삭제하고 미발행 초안을 읽을 수 있다.** 주소를 아무에게도 알리지 않았다는 것은 추측 난이도이지 권한 검사가 아니므로, 서비스를 공개하기 전에 끄고 역할 기반 권한으로 돌아간다. 기본값은 꺼짐이고, 켜진 상태에서 첫 요청이 오면 서버 로그에 `content_authoring_open`을 한 번 남긴다. 켜고 끄는 것은 그때까지의 발행 기록에 영향을 주지 않는다.

### 이 화면이 고치는 범위

초안은 기준 판본의 문서를 복사해 만들고, **문항·채점 규칙·힌트·해설은 서버에 그대로 남는다.** 브라우저로는 섹션·블록과 클래스 제목·소개·예상 시간만 오간다. 정답이 편집 화면으로 내려가지 않으므로, 이 화면을 여는 것과 정답을 보는 것은 다른 일이다.

그래서 지금 이 화면에서 **할 수 없는 일**도 분명하다. 새 클래스를 처음부터 만들기, 문항·정답·힌트·해설 작성, 진단·용어 편집은 아직 CLI 경로를 쓴다. 문항 묶음 블록은 기준 판본에 이미 있는 문항 중에서 고른다.

### 절차

1. 클래스를 고르고 **초안 만들기**. 판본 ID는 `classKey:v{다음 번호}`로 제안되며 직접 고칠 수 있다.
2. 단계를 고르고 블록을 추가·수정·이동·삭제한다. 블록 종류마다 전용 폼이 있고, 오른쪽 미리보기는 학습 화면과 같은 렌더러로 그린다.
3. **저장** 후 **검증**. 검증은 발행과 같은 dry run이라 참조 오류·중복 ID·낭독용 이름 누락까지 여기서 드러난다.
4. **발행**. 되돌릴 수 없으므로 확인 단계를 한 번 거친다. 발행하면 `ClassVersion` 행이 새로 생기고 초안은 잠긴다.

작성 중인 초안은 틀린 상태로도 저장된다. 검증을 통과해야 발행 버튼이 열리고, 이미 발행된 판본 ID로 발행하면 CLI와 같은 불변 오류로 거부한다. 발행한 초안은 더 고칠 수 없고, 다음 수정은 새 초안으로 만든다.

기존 수강자는 시작한 판본을 그대로 유지한다. 새 판본은 새로 수강하는 사람부터 보인다. 새 종류의 블록을 넣었다면 그 블록을 아는 앱이 먼저 배포되어 있어야 한다.

## 콘텐츠 내보내기·등록

검토된 DB 접속 환경의 서버/관리자 터미널에서 실행한다. `DATABASE_URL`은 해당 DB로 설정한다. 명령은 지정된 DB를 대상으로 하며 운영용 비밀값은 셸 기록이나 저장소에 적지 않는다.

```sh
npm run content:verify
npm run content:export -- --out /secure/path/content-export.json
npm run content:import -- --file /secure/path/reviewed-content.json --dry-run
npm run content:import -- --file /secure/path/reviewed-content.json
npm run content:verify
```

내보내기에는 정답·채점 규칙·힌트·해설이 포함된다. 파일은 `0600` 권한으로 새로 만들며 기존 파일을 덮어쓰지 않는다. 공개 API나 모바일 번들에 포함하지 않는다. 등록·검증 결과는 개수만 출력한다. 웹 사용자에게 등록 API를 제공하지 않는다.

번들 형식은 아래와 같다. 내보낸 파일을 복사해 편집하면 각 문서의 전체 형식을 확인할 수 있다.

```json
{
  "schemaVersion": 1,
  "skills": [],
  "classes": [],
  "diagnostics": [],
  "terms": []
}
```

`terms`는 나중에 추가한 항목이라 생략할 수 있다. 이전에 내보낸 번들 파일도 그대로 다시 등록된다.

필요한 항목만 넣는 부분 등록도 지원한다. 예를 들어 기존 개념을 참조하는 새 클래스만 넣고 `skills`와 `diagnostics`는 빈 배열로 두어도 된다. 개념 키는 기존 DB 또는 같은 번들에 반드시 있어야 한다. 파일 크기는 최대 5 MiB이며 큰 번들은 나누어 등록한다.

발행한 클래스/진단은 덮어쓰지 않는다. 수정하려면 `versionId`를 새로 부여한다. 내용이 바뀐 문항도 `problemVersionId`를 새로 부여하고 섹션·숙제 참조를 함께 변경한다. 클래스·진단의 같은 판본 ID에 동일 내용을 재등록하면 기존 판본을 변경하지 않는다. `Skill`은 같은 키로 이름·표시 순서를 갱신할 수 있다. MySQL이 JSON 객체 키 순서를 바꾸어도 의미가 같으면 동일한 내용으로 판단한다. 기존 해시는 다시 계산하지 않으며 새 판본 해시는 정렬된 JSON 키를 기준으로 계산한다.

새 클래스/진단 판본은 번들 배열 순서대로 발행된다. 같은 classKey/diagnosticKey를 가진 새 판본 중 마지막 항목이 최신이 된다. 내보내기도 발행 순서로 제공한다. 이미 있는 판본 재등록은 최신 판본을 되돌리지 않는다. 이전 내용으로 되돌리고 싶다면 새 판본 ID로 재발행한다.

등록 전 전체 참조와 문서 형식을 검사한다. 알 수 없는 필수 블록, 중복 ID, 없는 개념, 바뀐 기존 판본, 기존 문제 ID의 다른 내용, 클래스와 진단에 겹치는 문제 ID, 수식 `label`에 빠진 `labelAlt`, 수식 표기가 섞인 낭독용 이름은 거부한다. 용어에서는 없는 `termKey` 참조, 없는 `skillKey`, 판본마다 달라지는 용어의 개념, 본문에 없는 표층 문자열, 자신이 평가하는 개념을 문항 안에서 설명하는 주석을 거부한다. 쓰기는 한 DB 트랜잭션으로 처리하며 `--dry-run`은 쓰지 않는다.

## 용어 풀이와 진행도

본문에서 수학 용어에 설명을 달려면 `core.rich_text@2` 블록을 쓴다. 정의는 본문에 넣지 않고 `TermVersion`을 키로 참조한다. 정의를 고칠 때 그 용어를 쓰는 클래스를 모두 재발행하지 않기 위해서다.

```json
{
  "blockId": "fraction-addition:s1:b1",
  "kind": "core.rich_text",
  "typeVersion": 2,
  "required": true,
  "payload": {
    "text": "분모가 다르면 동치분수로 바꾸어 분모를 같게 만들어요.",
    "terms": [
      { "termKey": "term.denominator", "surface": "분모" },
      { "termKey": "term.equivalent-fraction", "surface": "동치분수" }
    ]
  }
}
```

`surface`는 본문에 실제로 있는 문자열이고, 같은 말이 여러 번 나오면 `occurrence`로 몇 번째를 가리킬지 정한다(기본값 1). 수식 구간 안의 글자는 세지도, 표시하지도 않는다. 조사가 붙은 "분모를"에서도 `surface`가 "분모"면 그 부분만 표시한다.

학습자에게 보일지는 서버가 구조만으로 정한다. 보이지 않기로 한 용어는 응답에서 아예 빠지고, 앱은 그 자리를 평문으로 그린다.

| 상황 | 결과 |
|---|---|
| 지금 배우는 클래스가 가르치는 개념의 용어 | 숨김 |
| 과제의 어느 문항이든 평가하는 개념의 용어 | 숨김 |
| 현재 클래스의 선수 개념, 또는 더 앞 순서 클래스가 가르치는 개념 | 보임 |
| 아직 배우지 않은 뒤 클래스의 개념 | 숨김 |
| 진단 문항 | 표시하지 않음 |

지금 배우거나 확인하는 개념을 그 자리에서 설명하면 수업과 평가를 대신하게 되기 때문이다. 문항 안에서 그 문항이 평가하는 개념을 주석하면 발행 단계에서 거부한다. 섹션 본문의 주석은 허용하고 위 표대로 노출만 조절한다. 이미 배운 개념 중 아직 연습이 필요한 것은 더 눈에 띄게 표시하며, 이 강조는 서버가 보내기로 한 용어에만 적용한다.

용어 정의는 클래스·진단과 달리 **항상 최신 판본을 조회해 보여준다**. 이미 시작한 클래스 판본과 과제 snapshot의 본문에서도 마찬가지다. 채점과 무관한 보조 설명이므로 판본을 고정하는 대신 정정이 즉시 반영되는 쪽을 택했다. 정의를 고치려면 새 `versionId`로 같은 `termKey`를 다시 발행한다. 기존 판본은 그대로 남는다.

용어 열람은 힌트와 다르다. 도움받은 풀이로 기록하지 않으며 개인화 판단에도 사용하지 않는다.

### 기본 용어 등록과 기존 클래스 주석

저장소의 `content/glossary-v1.json`은 정답이 없는 용어 전용 번들이라 그대로 등록할 수 있다.

```sh
npm run content:import -- --file content/glossary-v1.json --dry-run
npm run content:import -- --file content/glossary-v1.json
```

기존 클래스 본문에 주석을 다는 것은 별도 작업이다. 발행한 클래스는 불변이므로 `content:export`로 내려받아 해당 `core.rich_text` 블록을 위 형식으로 바꾸고, `public.versionId`를 새로 부여해 등록한다. 문항을 바꾸지 않으면 `problemVersionId`는 그대로 재사용한다. 기존 수강자는 이전 판본을 유지하고 새로 수강하는 사람부터 주석본을 받는다. 내보낸 파일에는 정답이 들어 있으므로 저장소에 커밋하지 않는다.

2026-09-15에 이 절차로 수식과 용어 주석을 담은 `v4` 판본 3개를 발행했다. 실행 기록은 [배포 문서](deployment.md)에 있다. 운영에서 실제로 보이는 조합은 다음과 같고, 나머지는 자기 개념이라 숨겨진다.

| 클래스 | 보이는 용어 |
|---|---|
| 분수, 전체와 조각의 관계 | (없음 — 모두 자기 개념) |
| 모양이 달라도 같은 분수 | 분수, 분모, 분자 |
| 분수 더하기, 조각 크기 맞추기 | 분수, 분모, 분자, 동치분수, 약분 |

## 물러난 블록

분수 막대만 그릴 수 있던 블록들은 새 콘텐츠에서 쓰지 않는다. 그림은 `core.scene@1` 하나로 그리고, 분수 막대는 그 안의 `strip` 도형으로 넣는다.

| 블록 | 상태 |
|---|---|
| `core.figure@1` | 발행된 판본이 계속 그려진다. 편집기에서 열어 고칠 수 있지만 새로 추가할 수는 없다. |
| `math.fraction_strip@1` | 위와 같다. |
| `math.fraction_sequence@1` | 완전히 제거했다. 발행된 콘텐츠가 없었다. 움직임은 `core.scene@1`의 `frames`로 만든다. |
| `math.fraction_builder@1` | 완전히 제거했다. 발행된 콘텐츠가 없었다. |

발행된 판본은 불변이라 고칠 수 없으므로, 이미 그 블록을 담은 클래스가 있는 한 검증 스키마와 렌더러는 남긴다. 스키마를 지우면 그 판본을 수강 중인 사람의 수업이 열리지 않는다. 편집기 팔레트에서 빼는 것과 앱에서 지우는 것은 다른 일이다.

## 학습 중 콘텐츠가 추가되면

새로 수강하는 사람에게 최신 클래스가 제공된다. 이미 수강한 사람은 시작했던 클래스 판본을 유지한다. 배정된 과제와 저장한 답안도 그대로다. 시작점 확인의 안내·문항 수·예상 시간은 DB에서 읽고, 시작한 진단은 그때 복사한 문항으로 끝까지 이어간다. 진단 개편만으로 진행 중인 진단을 교체하지 않는다. 완료 후 재진단을 안내하는 별도 UX는 후속 범위다.

## 검증

`tests/content-store.test.ts`에서 MySQL 초기 데이터, 내보내기 재등록, dry run, DB만으로 새 클래스·개념·진단 제공, 불변 판본·문항 보호, 과제와 진단 snapshot 보존을 검사한다. 용어는 발행·불변 판본·없는 참조 거부와, 클래스를 재발행하지 않고 정의를 고쳐 쓰는 경로를 함께 검사한다. 노출 규칙은 `tests/glossary.test.ts`, 본문 표시 위치 계산은 `tests/rich-text.test.ts`, 클래스·과제 응답에서의 실제 노출은 `tests/learning-integration.test.ts`에서 확인한다. 기존 채점·개인화·인증 테스트도 함께 실행한다. 전체 236개 테스트·타입 검사·웹/모바일 빌드를 통과했다. 로컬에서 이전 릴리스의 DB와 학습 기록을 생성한 뒤 새 migration을 적용해 기존 모든 행과 해시·시각·snapshot이 동일함을 확인했다. 운영에서도 migration·배포 성공과 공개 클래스 3개·블록·15문항의 이전 내용 일치를 확인했다. 이 검증은 수학 콘텐츠의 전문가 검수를 대신하지 않는다.
